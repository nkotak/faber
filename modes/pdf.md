# Mode: pdf — JD-Aligned CV Generation

You are generating a candidate CV that says the same true things `cv.md` says, but rewritten in the language of THIS specific JD. You are NOT highlighting keywords on top of existing bullets. You are making real decisions per bullet: keep / reorder / rewrite / drop — so a recruiter reading the CV against the JD thinks "this candidate speaks our language."

All rewriting happens inside Claude. Nothing on disk pre-processes cv.md. `generate-pdf.mjs` is a Playwright renderer only.

## Invocation

The mode can be invoked with a report path (`/faber pdf reports/156-clay-labs-2026-04-12.md`), a URL, or inline JD text. If a report path is provided, read the report and extract the `**URL:**` line to fetch the JD. If a URL is provided, fetch the JD. If JD text is pasted inline, use that directly. If none is available, ask the user.

The pipeline is 5 stages: **Analyze → Author → Assemble → Validate → Render & Log.** Each stage has clear inputs, outputs, and rules. The previous 8-stage breakdown was reorganized in 2026-04 — editorial structure replaced with functional structure. No loss of rigor; ~25% less prose.

## Stage 1 — Analyze

### 1.1 Sources of truth (read first)

1. `cv.md` — canonical CV. Every fact in the final HTML must trace here.
2. `modes/_profile.md` — user archetype framing, exit narrative, negotiation signature, superpower framing. Your rewriting voice anchors here.
3. `article-digest.md` — detailed proof points with metrics. If present, takes precedence over cv.md for any metric. Tolerate absence.
4. `config/profile.yml` — name, email, phone, LinkedIn, portfolio, github, location, target comp.
5. **Report Section E (only when invoked with a report path)** — `reports/{NUM}-{slug}-{DATE}.md` Section `## E) Personalization Plan`. Parse the 5-row table (`# | Section | Current state | Proposed change | Why`) into `personalization_plan = [{section, current_state, proposed_change, why}, ...]`. This is a **recommendation set** generated by the `offer` mode — it informs Stage 4 convergence checking, but **never overrides cv.md or the verb pool**. If the Plan suggests a change that violates Stage 2 truth rules (Rule 5: never import vocabulary cv.md doesn't claim, etc.), the Plan loses. If invoked without a report path, `personalization_plan = []`.

If a value cannot be sourced from these four canonical files, it does not exist. Do not invent.

### 1.2 Detect language and format

EN default. If JD is German, use `modes/de/` voice. If French, use `modes/fr/`. Paper format: US/Canada → `letter`; else → `a4`.

### 1.3 Ingest the JD with signal-density classification

| Section type | Signal | Treatment |
|---|---|---|
| Responsibilities, Requirements, "You will", "What you'll do" | High | Primary source for competencies and vocabulary |
| "Nice to have", "Bonus", "Preferred" | Medium | Secondary; single-mention items deprioritized unless repeated in high-signal |
| "About us", "What we offer", Benefits, Equal opportunity | Noise | Ignored for competency extraction. Company context only |

Conflict resolution: if signals contradict (e.g. "hands-on coding" + "manage 20+ engineers"), weight toward whichever phrasing appears more often AND in higher-signal sections. On tie, favor Responsibilities — it describes day-to-day work.

### 1.4 Build internal scratchpad (not emitted to user)

a. **Vocabulary** — 15-25 exact JD phrases (skills, systems, outcomes) from high+medium signal sections. Preserve casing. Don't normalize synonyms (keep both "evals" and "evaluation framework" if both appear). Note count + section type per phrase.

b. **Seniority cues** — IC / Senior / Staff / Principal / Director + scope signals ("partner with research", "own roadmap across N surfaces", "define strategy"). Trust responsibilities over title if they conflict.

c. **Top 5 required competencies** — composite-scored:
   - **Repetition** (4× high-signal outranks 2× anywhere)
   - **Section placement** (Responsibilities/Requirements = 3× weight; Nice-to-have = 1×)
   - **Phrasing force** ("must have"/"required"/"you will" = 3×; "experience with"/"familiarity" = 2×; "nice to have"/"bonus" = 1×)

   For each: operational definition in JD's own words + evidence trail (which phrases, how many times, which sections). Ties break toward more high-signal-section evidence.

d. **Archetype** — one of (AI Platform/LLMOps, Agentic/Automation, Technical AI PM, AI Solutions Architect, AI Forward Deployed, AI Transformation), qualified by `modes/_profile.md`. State reasoning in one sentence citing JD phrases.

e. **Domain context + red flags** — product area, customer type, scale, red flags (contradictory requirements, broad scope for stated level, >8 Requirements bullets, "wear many hats" at senior+).

### 1.5 Build the verb pool (truth anchor for Stage 2)

Extract every lead verb from cv.md Experience + Projects bullets (the first capitalized word of each `- ...` line). Group by role: `verb_pool[role.name] = unique lead verbs in that role`. This pool is the **only** allowed source of lead-verb substitutions in Stage 2 — a verb not in cv.md cannot be introduced even if the JD uses it. **Truth wins over diversity.**

### 1.6 Coherence check

1. Do top-5 competencies describe one job, or two? If JD is frankenstein (e.g. half ML-platform, half GTM-strategy), identify the primary cluster and deprioritize the outlier.
2. Does archetype match top-2 competencies? If not, re-derive from top-2.
3. Are vocabulary items ambiguous (e.g. "evaluation" = model evals or perf reviews)? Disambiguate or flag as lower-confidence.

### 1.7 Bullet-to-competency relevance matrix

**W2 role invariant (read before scoring any bullet):** Every W2 entry in cv.md (named employer + location + employment dates + employee-style role title) MUST appear in the final CV with real dates, company, and role header — no exceptions, including short tenures. Bullets are flexible (reorder/rewrite/drop individually); the role header is mandatory. A missing W2 creates a chronology gap that reads as a red flag.

For each cv.md bullet, classify:

- **Entry type:** W2 (named employer + location + dates + manager-style title) vs Project (solo / founder / open source / "Independent Researcher" / no hierarchy).
- **Relevance 0-3 per top-5 competency** (many-to-many):
    - 3 = directly proves competency using JD's exact vocabulary or near-synonym
    - 2 = proves competency in different vocabulary → rewrite candidate
    - 1 = touches competency tangentially
    - 0 = unrelated to any top-5 competency
- **Competency weights:** competency #1 = 5, #2 = 4, #3 = 3, #4 = 2, #5 = 1.
- **Weighted score per bullet:** `weighted_score = Σ (relevance_i × weight_i)`. Used for ordering bullets within a role. Fill/drop/guardrail rules continue to use the per-competency relevance values and the bullet's *max* relevance across competencies, so "relevance-0 bullet" still means max-per-competency relevance = 0.
    - *Example.* JD top-5: #1 platform consolidation (w=5), #2 agentic systems (w=4), #3 SDK scale (w=3), #4 observability (w=2), #5 RL depth (w=1).
        - Bullet A: relevance {#1: 2, #5: 2}. Flat sum = 4. Weighted = 2·5 + 2·1 = **12**.
        - Bullet B: relevance {#1: 0, #5: 2, #4: 2}. Flat sum = 4. Weighted = 2·1 + 2·2 = **6**.
    - Flat aggregation ties them; weighted places A above B because A's hit lands on the most important competency.

Build the coverage table internally. It feeds Stage 2.

## Stage 2 — Author

Apply the 3-question decision per bullet, in order:

**Q1. Does it prove anything the JD asks for?**
- No (max relevance = 0) → **drop candidate** (still true, just not for this JD). NOTE: only executed if the parent W2 still has ≥2 kept bullets after the drop. If dropping breaches the 2-bullet floor, retain **verbatim** (no JD-vocab rewrite) to preserve the chronology anchor.
- Yes → Q2.

**Q2. Does the bullet's current language already match the JD's vocabulary?**
- Yes → **keep verbatim** (reorder among peer bullets in Stage 3).
- No → Q3.

**Q3. Can I rewrite to JD vocabulary WITHOUT changing what happened, WITHOUT adding a metric/tool/scope not in cv.md, and WITHOUT claiming a skill not in cv.md Core Skills?**
- Yes → **rewrite** per the 9 rules below.
- No → **keep verbatim** (truth wins over vocab alignment).

A "yes" to Q3 means the underlying technical reality is the same and the JD's phrase is an accurate description of what happened. Examples:
- "ML-driven orchestration" → "agentic orchestration": YES if the system has autonomous decision loops (the Disney PPO bullet qualifies).
- "ML-driven orchestration" → "multi-agent orchestration": NO if there was one agent, not multiple.
- "LLM workflows with retrieval" → "RAG pipelines": YES if retrieval was vector-based and generation was augmented by it.

### Rewriting rules (when Q3 says yes)

1. **Preserve every number.** $300M operating income, 250M+ subscribers, 10B+ annual requests, 50K TPS, 99.99% reliability, $25M cost savings, $1K MRR, 70+ stars, 15 use cases, 70+ engineers, 4 principal architects, 25+ markets, 30% engagement, $10M SMS savings. Numbers never change. If you can't keep the number, don't rewrite.
2. **Preserve every named tool and system.** Stripe, OpenSearch, Databricks, Salesforce Marketing Cloud, Next.js, Depth Anything V3, PPO, GRPO, BitNet, YOCO. Truth anchors.
3. **One idea per bullet.** Don't bolt a second idea on to hit a second keyword; split or drop instead.
4. **Action verb front-loaded, JD vocabulary woven in.** "Shipped agentic orchestration for 250M subscribers" beats passive constructions.
5. **Never import vocabulary for skills cv.md doesn't have.** If the JD says "fine-tuning" and no cv.md bullet reflects fine-tuning, no rewrite may imply it. That gap goes unaddressed, period.
6. **Length parity ±15%.** Longer rewrites almost always indicate invention.
7. **Verb-pool-bounded substitution** *(replaces the old "Shipped stays shipped" rule, which over-blocked and created collision permanence)*. Lead-verb substitution is permitted only when the new verb already appears as a lead verb for some bullet in `cv.md` — i.e., it must be in the `verb_pool` from Stage 1.5. The new verb must also be **accurate** for what this specific bullet describes (substituting "Mentored" for a deployment bullet is fabrication even if "Mentored" is in the pool). Adjective upgrades within the bullet body are still prohibited (no "spearheaded", "pioneered", "architected" unless cv.md already says them).
8. **No banned phrases.** Banned phrases from `modes/_shared.md:109-133` apply — no "leveraged", "facilitated", "seamless", "robust", "cutting-edge", "passionate about", "demonstrated ability".
9. **Cross-bullet collision check.** Before committing a rewrite, scan the in-progress assembled bullet list. If the proposed lead verb is already used by another rewritten bullet in this render, choose the next available accurate verb from `verb_pool[role]`. If the pool is exhausted for this bullet, revert to cv.md verbatim. The collision check runs *every* commit, so verbs assigned earlier in the render constrain verbs assigned later.

## Stage 3 — Assemble

Fill the placeholders in `templates/cv-template.html`. Section order: Header → Work Experience → Projects → Education → Skills.

### 3.1 Header

Name, email, LinkedIn, **portfolio URL**, location from `profile.yml`. The portfolio URL belongs here in the contact row — this is where recruiters scan first. (Previously the URL was duplicated into a Professional Summary; the Summary section was removed in 2026-04 because it ate vertical space without earning it. Recruiters either skim past Summaries or read content already proven by the bullets below.)

### 3.2 Work Experience (W2 only, reverse chronological)

- Every W2 from cv.md appears with real dates/company/role title (W2 invariant).
- Within each role, bullets ordered by **weighted score** (descending). Tie-breakers: (a) higher single-competency relevance hit on the top-ranked competency (#1 wins over #2, etc.); (b) cv.md original order. Kept-verbatim bullets do NOT get ordering priority — a rewritten bullet with a higher weighted score ranks above a verbatim one with lower score.
- Drop relevance-0 bullets if the role still has ≥3 kept bullets after drop.
- **Target 3 bullets per role. Hard floor: 2 bullets.** If relevance-2+ count <3, fill with relevance-1. If relevance-1+ count is still <2, fill with relevance-0 **verbatim** from cv.md — do NOT apply Stage 2 rewrites to relevance-0 fillers (rewriting toward a competency a bullet doesn't prove is fabrication). Short-tenure roles whose cv.md entry has only 2-3 bullets may naturally land at the 2-bullet floor.
- Apply Stage 2 rewrites only to relevance-1+ kept bullets.

### 3.3 Projects (1-3 from cv.md, ranked by weighted score)

- **Founder-promotion rule:** if a cv.md project is led as Founder / Co-Founder / CEO / Founding-{X} AND the JD explicitly values founder experience (Series A, startup, "founded a company" in requirements, 0→1 roles), promote it to Professional Experience immediately after the most recent W2. Gets W2 treatment with full bullet count. Otherwise it stays in Projects. (At time of writing: Roominary.ai qualifies.)
- **Independent-research split rule:** if cv.md has a single "Independent Researcher" / "Open Source" parent listing multiple distinct named projects, show each as a SEPARATE Project entry — don't fuse under one heading. (At time of writing: YOCO-BitNet and Multi-Layer GRPO are two named projects under one Independent Researcher entry.)
- **Selection bias:** prefer research-adjacent projects for research / frontier-lab / AI-infrastructure / model-building JDs; prefer founder / 0-1 projects for startup / Series-A / product-leadership JDs. Ties on weighted score break in cv.md document order.
- Each shown project gets its cv.md bullets, Stage 2 applied.

### 3.4 Education

Unchanged from cv.md.

### 3.5 Skills

Read ALL Core Skills categories from cv.md (cv.md is the source of truth; at time of writing: AI/ML, Product, Technical, Prototyping — add categories in cv.md to flow them through). Reorder categories so the JD-most-relevant leads. Within each category, reorder comma-separated items by JD weighted relevance, front-loading JD-matched items. Keep all items visible (no truncation). Never add an item not already in cv.md (hallucination rule). If the JD calls for a category cv.md doesn't have, that gap goes unaddressed — do not invent.

### 3.6 Post-assembly verb-collision audit

Count distinct lead verbs across all rendered bullets. For any verb appearing 3+ times, keep its two highest-weighted occurrences and demote the rest: substitute with the next accurate verb from `verb_pool[role]` that isn't already used; if no truth-anchored alternative exists, revert to cv.md verbatim. **Truth always wins over diversity** — collisions are tolerated when the pool is exhausted. This audit catches 3-way ties that emerged only after final ordering, when Stage 2 Rule 9's per-bullet check couldn't see them.

## Stage 4 — Validate

Run as a deterministic checklist before rendering. If any check fails, fix and re-check.

### 4.1 Truth and structure

- [ ] Every W2 role in `cv.md` Experience appears with real dates/company/role title (no W2 dropped, including short tenures).
- [ ] Every W2 role has ≥2 bullets; relevance-0 fillers (if used) are verbatim from cv.md, not rewritten.
- [ ] Every number in output traces to `cv.md` or `article-digest.md`.
- [ ] Every named tool traces to `cv.md`.
- [ ] Every claimed skill is in `cv.md` Core Skills (or a direct synonym).
- [ ] No banned phrases from `modes/_shared.md:109-133`.
- [ ] No em-dashes / en-dashes / smart quotes / ellipsis / non-breaking spaces (generate-pdf.mjs normalizes anyway, but don't generate them).
- [ ] Each rewritten bullet within ±15% length of its cv.md original.
- [ ] No duplicate metric reused across two bullets (70+ engineers appears once, not recycled).
- [ ] Founder-type projects placed per Stage 3.3 rule (Projects by default; promote to Experience iff JD values founder credibility).
- [ ] Multi-project "Independent Researcher" entries shown as separate Projects, not fused under one heading.
- [ ] Bullet count per W2: target 3, floor 2 (short-tenure roles may sit at floor).
- [ ] Within each W2, bullets ordered by weighted score (descending); ties broken by top-competency hit, then cv.md order — a relevance-2 hit on competency #1 outranks a relevance-2 hit on competency #5.

### 4.2 ATS-specific

- [ ] **Section headers use standard ATS-parseable names:** Work Experience, Projects, Education, Skills (NOT Career, My Journey, Experience, Career History).
- [ ] **Section headers render as `<h2>` elements**, not styled `<div>`. (Workday, Greenhouse, Lever, BambooHR all chunk by heading semantics — `<div>` is invisible to chunking.)
- [ ] **All dates render as "Mon YYYY" or "Mon YYYY – Mon YYYY" or "Mon YYYY – Present"** (regex: `^(Jan|Feb|Mar|Apr|May|Jun|Jul|Aug|Sep|Oct|Nov|Dec)\s+\d{4}(\s+–\s+(Present|(Jan|Feb|...|Dec)\s+\d{4}))?$`). Year-only dates from cv.md (e.g. Independent Researcher "2024 – Present") are tolerated.
- [ ] **All skill items in `<span class="skill-item">`** with real text (no CSS-hidden text, no `::before` content tricks).
- [ ] **No lead verb appears 3+ times** across all rendered bullets (Stage 3.6 enforced this; verify).
- [ ] Single column, UTF-8.

### 4.3 Archetype clarity (HR Reviewer perspective)

- [ ] The first bullet of the most-recent W2 lands the archetype (high relevance to the top-1 or top-2 competency). If not, reorder within that role so the strongest archetype-aligned bullet leads. Recruiters scan top-down; the first bullet of the most-recent role is the most-read line on the CV.

### 4.4 Page target

- [ ] Page target: 1 page. `generate-pdf.mjs` auto-fits by progressively tightening layout (margins → font size → spacing), preserving content. Dropping bullets is the last resort and only triggers if all layout levers are exhausted.

### 4.5 Personalization Plan convergence (only if `personalization_plan` was loaded in Stage 1.1)

For each of the 5 changes in the Plan, classify the assembled CV's treatment:

- **APPLIED** — the assembled CV reflects the Plan's proposed change (e.g., Plan said "lead Disney with API consolidation"; assembled CV does).
- **DIVERGED** — the assembled CV did not apply the change. Cite the Stage 1-3 reason (e.g., "Plan suggested promoting Roominary to Experience, but JD doesn't value founder credibility per Stage 1.4 archetype detection").
- **REJECTED** — the change cannot be applied without violating truth rules (e.g., "Plan suggested adding a fine-tuning bullet, but cv.md has no fine-tuning evidence — Stage 2 Rule 5 forbids the import").

The convergence breakdown is logged in Stage 5.4. **The Plan never overrides cv.md, the W2 invariant, the verb pool, or any other Stage 1-4 rule.** If a Plan change conflicts with a hard rule, the Plan loses and the bullet stays as the rules dictate. The convergence log makes evaluation→PDF coherence visible: if too many DIVERGED/REJECTED rows show up, that's a signal the evaluation report and the PDF are out of sync and one of them needs revisiting.

## Stage 5 — Render & Log

### 5.1 Fill the template

Fill every `{{...}}` placeholder in `templates/cv-template.html`:

| Placeholder | Content |
|-------------|---------|
| `{{LANG}}` | `en` / `es` / `de` / `fr` |
| `{{PAGE_WIDTH}}` | `8.5in` (letter) or `210mm` (a4) |
| `{{NAME}}`, `{{EMAIL}}`, `{{PHONE}}`, `{{LINKEDIN_URL}}`, `{{LINKEDIN_DISPLAY}}`, `{{PORTFOLIO_URL}}`, `{{PORTFOLIO_DISPLAY}}`, `{{LOCATION}}` | from `config/profile.yml` |
| `{{SECTION_EXPERIENCE}}` | "Work Experience" / language equivalent |
| `{{EXPERIENCE}}` | Stage 3.2 output (W2 roles, reordered/rewritten) |
| `{{SECTION_PROJECTS}}` | "Projects" / equivalent |
| `{{PROJECTS}}` | Stage 3.3 output (1-3 Projects) |
| `{{SECTION_EDUCATION}}` | "Education" / equivalent |
| `{{EDUCATION}}` | Stage 3.4 output |
| `{{SECTION_CERTIFICATIONS}}`, `{{CERTIFICATIONS}}` | Empty strings or omit if cv.md has no certifications |
| `{{SECTION_SKILLS}}`, `{{SKILLS}}` | Stage 3.5 output |

The template no longer carries `{{SECTION_SUMMARY}}` or `{{SUMMARY_TEXT}}` — the Professional Summary section was removed in 2026-04.

**Note on `{{NAME}}`**: render verbatim from `config/profile.yml`'s `full_name` field. Do NOT apply title-case, all-caps, or any other case transform. The header h1 styles the name visually (and explicitly sets `text-transform: none` to defend against inheritance); the source string casing in profile.yml is canonical. If profile.yml says "Alex Chen", the rendered PDF says "Alex Chen" — never "ALEX CHEN".

**Note on `{{PHONE}}`**: render verbatim from `config/profile.yml`'s `phone` field. The phone number belongs in the CV header contact row (recruiters expect it) — this is distinct from the privacy rule in `batch/batch-prompt.md` that forbids sharing phone in outbound *messages* (cold emails, LinkedIn DMs, application form answers).

Write to `/tmp/cv-candidate-{company-slug}.html`.

### 5.2 Filename convention (canonical, must match)

- **Input report path:** `reports/{REPORT_NUM}-{company-slug}-{YYYY-MM-DD}.md` → extract `{REPORT_NUM}` (e.g. `156`) and `{company-slug}` (e.g. `clay-labs`) from the filename.
- **Output PDF path:** `output/cv-{REPORT_NUM}-{company-slug}-{YYYY-MM-DD}.pdf`
  - Example: `output/cv-156-clay-labs-2026-04-21.pdf`
  - The dashboard's PDF column and "P open PDF" keybinding use regex `^cv-(\d+)-.*\.pdf$` — any deviation from this prefix breaks both.

### 5.3 Render via generate-pdf.mjs

```bash
node generate-pdf.mjs /tmp/cv-candidate-{company-slug}.html output/cv-{REPORT_NUM}-{company-slug}-{YYYY-MM-DD}.pdf --format={letter|a4}
```

**Auto-fit ladder** (built into `generate-pdf.mjs`): the generator tries to land on 1 page without dropping content. It walks the ladder, stopping the moment the rendered PDF is 1 page:
1. Margin: 0.6in → 0.5 → 0.4 → 0.3 → 0.25in
2. Body font-size (via injected style): 11px → 10.5 → 10px (paired with 0.25in margin)
3. Section margins + line-height tightening (section margin-bottom 18→14→12px, line-height 1.6→1.5)
4. **Last resort only:** generator reports `pageCount>1`; Claude drops the lowest-weighted bullet within the longest W2 role and re-renders. Max one bullet per run. If still >1 page, report to user rather than silently emit 2 pages or further truncate.

Layout levers (1-3) preserve content exactly. Step 4 is never silent.

### 5.4 Decision log (emit every time)

Format as a collapsible block. The decision log is auditable — if any rewrite can't be justified against cv.md, revert that bullet to verbatim before emitting the PDF.

## Canva CV generation (optional)

If `config/profile.yml` has `canva_resume_design_id` set, offer the user a choice before generating:
- **"HTML/PDF (fast, ATS-optimized)"** — the existing flow above
- **"Canva CV (visual, design-preserving)"** — the flow below

If the user has no `canva_resume_design_id`, skip this prompt and use HTML/PDF.

### Canva workflow

#### Step 1 — Duplicate the base design

a. `export-design` the base design (using `canva_resume_design_id`) as PDF → get the download URL.
b. `import-design-from-url` using that download URL → creates a new editable design (the duplicate).
c. Note the new `design_id` for the duplicate.

#### Step 2 — Read the design structure

a. `get-design-content` on the new design → returns all text elements (richtexts) with their content.
b. Map text elements to CV sections by content matching:
   - Look for the candidate's name → header section
   - Look for company names from cv.md → experience sections
   - Look for degree/school names → education section
   - Look for skill keywords → skills section
c. If mapping fails, show the user what was found and ask for guidance.

(Note: the HTML/PDF flow no longer renders a Professional Summary section. If the Canva base design has a Summary text box, leave it as-is from the template, or have the user manually clear it before duplicating — Faber will not auto-populate it.)

#### Step 3 — Generate tailored content

Same content generation as the HTML flow:
- Reorder experience bullets by JD weighted relevance (Stage 1.7 + Stage 3.2 rules).
- Reorder Skills categories and within-category items by JD relevance.
- Inject JD vocabulary naturally into existing content (NEVER invent).

**IMPORTANT — Character budget rule:** each replacement text MUST be roughly the same length as the original (within ±15% character count). The Canva design has fixed-size text boxes — longer text causes overlap with adjacent elements. Count characters per element from Step 2 and enforce this budget.

#### Step 4 — Apply edits

a. `start-editing-transaction` on the duplicate design.
b. `perform-editing-operations` with `find_and_replace_text`:
   - Replace each experience bullet with reordered/rewritten bullets.
   - Replace Skills text with JD-reordered categories and items.
   - Replace project descriptions with top relevant projects (selected per Stage 3.3).
   - If the base design has a "Core Competencies" or "Key Skills" tag area, leave empty or populate from top-ranked Skills items — do NOT invent a separate competency list.
c. **Reflow layout after text replacement:**
   1. Read updated element positions/dimensions from the response.
   2. For each work experience section (top to bottom), calculate `end_y = top + height`.
   3. The next section's header should start at `end_y + consistent_gap` (use the original gap from the template, typically ~30px).
   4. Use `position_element` to maintain even spacing.
   5. Repeat for all work experience sections.
d. **Verify layout before commit:**
   - `get-design-thumbnail` with the transaction_id and page_index=1.
   - Visually inspect for: text overlap, uneven spacing, text cut off, text too small.
   - Adjust with `position_element`, `resize_element`, `format_text` until clean.
e. Show the user the final preview; ask for approval.
f. `commit-editing-transaction` to save (ONLY after user approval).

#### Step 5 — Export and download PDF

a. `export-design` the duplicate as PDF (format: a4 or letter based on JD location).
b. **IMMEDIATELY** download the PDF (the export URL is a pre-signed S3 link expiring in ~2 hours):
   ```bash
   curl -sL -o "output/cv-{candidate}-{company}-canva-{YYYY-MM-DD}.pdf" "{download_url}"
   ```
c. Verify with `file output/...pdf` — must show "PDF document". If XML/HTML, the URL expired — re-export and retry.
d. Report PDF path, file size, Canva design URL (for manual tweaking).

#### Error handling

- If `import-design-from-url` fails → fall back to the HTML/PDF pipeline with a message.
- If text elements can't be mapped → warn the user, show what was found, ask for manual mapping.
- If `find_and_replace_text` finds no matches → try broader substring matching.
